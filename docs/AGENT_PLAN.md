# 方案 V2:面向 Agent 应用开发岗位的版本

> 本文在 `DESIGN.md`(执行引擎设计)之上增加 **Agent 层**。执行引擎部分不变,仍是评分的核心;
> Agent 层用来体现"大模型 Agent 应用开发"的能力。

## 0. 先搞懂 DAG(举个例子)

**DAG = 有向无环图**。每个"步骤"是一个点,"谁必须先做完"是一个箭头,并且不能绕成圈。

做一顿饭:

```
淘米 ─► 煮饭 ─────────────────┐
洗菜 ─► 切菜 ─► 炒菜 ──────────┴─► 装盘 ─► 上桌
```

- "煮饭"和"炒菜"没有依赖关系,可以**同时做**(并行)。
- "装盘"要等"煮饭"和"炒菜"**都完成**才能开始(依赖)。
- 如果"炒菜"烧糊了:只需要重做"炒菜",不用重新淘米、洗菜、煮饭(**步骤级重试 + 复用已完成结果**)。
- 不能出现"炒菜等装盘,装盘又等炒菜"这种环,否则永远做不完(所以叫"无环")。

动画素材"角色替换"的 DAG:

```
probe(探测) ─► extract_frames(拆帧) ─► segment_0..N(抠出原角色, GPU, 分块并行) ─┐
   │                                                                              ├─► swap_0..N(替换角色, GPU)
   ├─► gen_reference(按描述生成新角色参考图, GPU, 结果有随机性) ─────────────────────┘        │
   └─► extract_audio(提取音轨) ───────────────────────────────────────────────┐              ▼
                                                                              │       assemble(合成视频)
                                                                              └──────────────┤
                                                                                             ▼
                                                                                   mux ─► quality_check ─► human_approval ─► publish
```

- 为什么 `segment`/`swap` 要分块:一段视频拆成 N 块,**某一块失败只重做那一块**;块之间还能并行。
- 为什么 `gen_reference` 要单独成步并保存结果:生成式模型每次结果都不一样,如果下游失败后连它一起重算,
  新角色的长相就变了,前后不一致。**必须把它的结果固化下来复用**。
- 为什么 `publish` 要单独成步:它会对外产生影响(发布到素材库),重复执行会产生重复发布,所以要带幂等键。

> 题目没规定具体业务,以上是我选定的示例。引擎对"步骤做什么"无感知,换业务只需要换模板和 MOCK 步骤。

## 1. 一句话定位

> **LLM Agent 负责"想"(规划、诊断),可靠执行引擎负责"做"(执行、重试、恢复、记录)。**
> Agent 不直接干重活,它只通过受控的"工具"去调用引擎。

这和主流 Agent 工程实践一致:LLM 不可靠,所以要**把 LLM 的输出当作不可信输入去校验,把 LLM 的决策结果持久化,
把有副作用的动作放到确定性的系统里执行**。

```
用户: "把这段视频里的主角换成红发女孩,发布到素材库"
        │
        ▼
 ┌──────────────┐   结构化输出    ┌─────────────┐   通过   ┌──────────────────────┐
 │ Planner Agent│ ──(JSON 计划)─► │ 计划校验器    │ ───────► │ 持久化执行引擎 (DESIGN.md) │
 │  (LLM)       │ ◄──校验失败反馈── │ 白名单/环/预算 │         │ DAG·重试·恢复·缓存·可观测 │
 └──────────────┘                 └─────────────┘         └───────────┬──────────┘
                                                                      │ 步骤失败/卡死
                                                                      ▼
                                              ┌──────────────────────────────┐
                                              │ Diagnosis Agent (LangGraph)   │
                                              │ 读状态/错误 → 诊断 → 建议动作  │
                                              │ ──► 人工确认(interrupt)──► 执行 │
                                              └──────────────────────────────┘
        所有 LLM 调用 → llm_calls 表(prompt、输出、token、耗时、成本),可追溯
```

## 2. 面试能讲到的 Agent 概念 ↔ 本项目落点

| 概念 | 在本项目中的体现 |
|---|---|
| **Tool / Function Calling** | Agent 通过一组工具(提交任务、查状态、重试步骤、取消…)操作引擎 |
| **结构化输出(Structured Output)** | Planner 输出 Pydantic 校验的 JSON 计划,而非自由文本 |
| **Planner–Executor 分离** | LLM 只出计划,执行交给确定性引擎 |
| **ReAct / 工具循环** | Diagnosis Agent:观察(读错误)→ 思考 → 行动(建议动作)→ 再观察 |
| **Guardrails(护栏)** | 步骤类型白名单、DAG 合法性、成本/帧数上限、写操作需确认 |
| **Human-in-the-Loop** | 人工审批步骤;诊断后的"重试/跳过"需人确认(LangGraph `interrupt`) |
| **Durable Execution / Checkpoint** | 引擎的步骤级恢复;Diagnosis Agent 用 LangGraph checkpointer 保存自身状态 |
| **幂等与副作用控制** | `publish` 幂等键;Agent 的工具调用不会因重试而重复生效 |
| **MCP(Model Context Protocol)** | 把引擎能力以 MCP Server 暴露,任意 MCP 客户端(Cursor 等)可直接调用 |
| **LLM 可观测(Tracing)** | 每次 LLM 调用的 prompt/输出/token/成本/耗时入库并关联到任务 |
| **Eval(评测)** | Planner 评测集:计划合法率、依赖正确率、护栏拦截率 |

## 3. 技术选型(贴合 Agent 应用开发岗位)

| 用途 | 选型 | 理由(面试可答) |
|---|---|---|
| 语言 | Python 3.11 | Agent 生态主流语言 |
| 接口层 | FastAPI + Pydantic v2 | Agent 服务事实标准;Pydantic 同时用于 API 校验、结构化输出、工具参数 schema |
| LLM 接入 | `openai` SDK(OpenAI 兼容协议) | DeepSeek/通义/OpenAI 等都兼容,换模型只改 `base_url`+`model` |
| 无 Key 兜底 | **MockLLM**(同一接口,确定性脚本回复) | 测试可复现、不花钱;**明确标注评测结果来自 Mock,不代表真实模型水平** |
| Agent 编排 | **LangGraph**(仅用于 Diagnosis Agent) | 当前最常被问到的 Agent 编排框架;自带 checkpoint 与 `interrupt`,正好对应"可恢复 + 人工介入" |
| Planner | **手写**(结构化输出 + 校验 + 失败回灌重试) | 用最少代码讲清原理,避免"框架黑盒" |
| 工具协议 | **MCP**(官方 Python SDK `mcp`) | 近年工具接入的标准协议 |
| 持久化 | SQLite(WAL) | 同 DESIGN.md:简单、可控、易解释 |
| 执行引擎 | 自研(不用 Temporal/Celery) | 题目要求"更简单、更可控、更易解释";文档中说明何时该换 |
| 测试 | pytest + httpx | 故障注入与不变量测试 |

> 不选 LangChain 的原因(面试可说):抽象层多、版本变动快,本项目只需要"LLM 调用 + 工具 + 状态图",
> 手写 + LangGraph 足够;能说明取舍比堆框架更重要。

## 4. 功能清单

### 4.1 必须实现(Must)

**A. 执行引擎(DESIGN.md 全部核心)**
1. 任务/步骤/尝试/事件/产物 的 SQLite 模型与单一状态转换入口
2. DAG 依赖、环检测、静态 fan-out 展开
3. 认领 + 租约 + 心跳(按进展续租)+ fencing token + 过期回收
4. 子进程隔离执行,超时/卡死可强杀,父死子自杀
5. 失败分类 + 退避重试 + 步骤级人工重试 + 任务 resume
6. 内容寻址产物缓存 + 校验 + 结果复用
7. 步骤内检查点
8. FastAPI 查询/控制接口 + 简易 Dashboard
9. 故障矩阵测试 F1~F13(含 `kill -9` 与混沌测试)

**B. 最小 Agent 层**
10. **LLM 客户端抽象**:`LLMClient`(OpenAI 兼容)+ `MockLLM`,统一超时/重试/token 计数
11. **Planner Agent**:自然语言 → 结构化 JSON 计划 → 校验 → 校验失败把错误回灌给 LLM 重试(最多 N 次)→ 通过后落库并提交引擎
    - 护栏:步骤类型白名单、DAG 合法、分块数/帧数/预算上限
    - **计划持久化**:恢复时不重新问 LLM(LLM 输出也是需要固化的产物)
12. **Agent 工具集**(带 Pydantic 参数 schema,读/写分级):
    - 读:`get_task`、`list_tasks`、`get_step_attempts`、`get_events`
    - 写:`submit_plan`、`retry_step`、`resume_task`、`cancel_task`(写操作带幂等键)
13. **LLM 调用追踪(最小版)**:`llm_calls` 表记录 prompt、输出、token、耗时、关联 task_id

### 4.2 可选实现(Optional,已选定全部,按优先级排序)

| 优先级 | 功能 | 说明 | 预估 |
|---|---|---|---|
| O1 | **人工审批步骤** | DAG 中的 `human_approval` 步骤:状态 `AWAITING_APPROVAL`,通过 API 批准/拒绝后继续;可能挂数小时,体现"长时间等待也不占 worker" | 1h |
| O2 | **Diagnosis Agent(LangGraph)** | 步骤最终失败时触发:读取错误/尝试历史 → LLM 诊断并给出建议动作(重试/降参数重试/放弃)→ `interrupt` 等人确认 → 调用工具执行;使用 SqliteSaver 做 checkpoint,**进程重启后可继续** | 2h |
| O3 | **MCP Server** | 用 MCP 暴露第 12 条中的工具,可在 Cursor 里直接用自然语言查询/操作任务 | 1h |
| O4 | **Trace 增强** | 在 Dashboard 展示任务下所有 LLM 调用、token 与估算成本、各 Agent 决策与人工确认记录 | 1h |
| O5 | **Planner 评测集** | 20~30 条自然语言需求 + 期望约束(必含步骤、依赖正确、护栏拦截);指标:合法率、一次通过率、平均修复轮数。**无真实 Key 时跑 Mock,并在报告中标注** | 1.5h |
| O6 | GPU 槽位 / 资源画像演示 | 同 DESIGN.md 第 11 节 | 0.5h |

> **时间提醒**:引擎部分约 9.5h,Agent 层(必须项 B + 可选项)约再 8~9h。
> 笔试"至少完成一题",质量优先。**若时间紧,按 O1 → O2 → O5 → O3 → O4 → O6 顺序保留,
> 但引擎的故障测试(F1~F13)不得被牺牲**——它是评分的核心。

## 5. 对 DESIGN.md 的增量改动

- 步骤状态新增 `AWAITING_APPROVAL`(人工审批,不占用 worker、不计超时;批准 → `SUCCEEDED`,拒绝 → `FAILED(PERMANENT)`)。
- 新增表:`plans`(自然语言需求、LLM 原始输出、校验结果、最终计划)、
  `llm_calls`(调用追踪)、`approvals`(审批与人工确认记录)。
- 任务规格来源改为"计划":`task.spec` 可由模板生成,也可由 Planner 生成;**二者校验器相同**。
- 新增步骤类型 `gen_reference`(非确定性,强调"固化产物复用")、`segment`/`swap`(GPU,分块)、`human_approval`。

## 6. 面试讲解主线(建议)

1. **问题**:长时间 AI 任务,失败/中断怎么办?→ DAG + 步骤级恢复 + 结果复用。
2. **关键机制**:租约 + fencing(至少一次执行、恰好一次提交)、按进展续租(区分慢和死)、内容寻址缓存。
3. **为什么需要 Agent**:用户用自然语言描述需求 → Planner 生成计划;失败后不是只会报错,而是 Diagnosis Agent 读历史给建议。
4. **如何约束 LLM**:结构化输出 + 校验 + 白名单 + 预算 + 写操作人工确认;LLM 决策持久化,恢复不重问。
5. **可观测**:任务/步骤/事件/LLM 调用统一可查;MCP 暴露能力。
6. **诚实的局限**:见失败案例章节(Mock LLM 的评测局限、SQLite 单机、子进程不等于容器等)。

## 7. 预先承认的局限(Agent 层新增)

- 无真实 LLM Key 时,Planner/Diagnosis 的"智能程度"无法验证,只能验证**系统管线和护栏**是否正确。
  接入真实模型后需要重新跑评测并报告差异。
- Diagnosis Agent 的建议质量取决于模型;系统只保证"建议不会在未确认时被执行"。
- LangGraph 版本迭代较快,锁定版本并在 README 记录;其 checkpoint 与引擎状态是**两套持久化**,需要保证"以引擎为准"。
- MCP 暴露写工具存在被误用的风险,默认只开放读工具,写工具需显式开启。
